# مخطط العمارة الأولي

## الهدف

تجهيز إطار معماري مناسب لنظام صيدلية يعمل محليًا، ويعتمد على أمان البيانات، سرعة البيع، ومقاومة ضعف الإنترنت. هذا الملف يمثل نقطة البداية قبل اعتماد التقنية النهائية في المراحل التالية.

---

## 1) مبادئ العمارة

1. Local-first: يعمل النظام بشكل أساسي بدون اتصال مستمر.
2. Audit-first: كل حركة حساسة تُسجل وتُراجع.
3. Batch-aware: المخزون يُدار حسب الدفعة والصلاحية.
4. Human approval for import: أي ملف مستورد يحتاج مراجعة بشرية قبل التأثير.
5. Safe rollback: لا يتم حذف الحركات، بل تعكس أو تُلغى عبر قيد جديد.
6. Future-ready: تم ترك مساحة للعيادة لاحقًا دون بناءها داخل MVP.

---

## 2) طبقات النظام

### الطبقة 1: Experience Layer

- واجهة نقطة البيع
- إدارة المنتجات والكتالوج
- شاشة الاستيراد والمراجعة
- الشاشة المالية والورديات
- تقارير التشغيل والمدققين

### الطبقة 2: Application Layer

- خدمات البيع
- خدمات المخزون
- خدمات المشتريات
- خدمات الاستيراد
- خدمات الحسابات والوردية
- خدمات التقارير والتدقيق

### الطبقة 3: Domain Layer

- Product
- Batch
- Supplier
- Purchase Order
- Invoice
- Return
- Shift
- Cash Drawer
- Inventory Ledger
- Prescriptions
- Patient Lite

### الطبقة 4: Data Layer

- قاعدة محلية للعمليات اليومية
- سجل حركات كاملة
- طباعة/نسخ احتياطي
- إمكانية مزامنة لاحقة مع خادم مركزي أو خدمة سحابية اختيارية

---

## 3) نموذج التشغيل

### التشغيل المحلي

- كل فرع يعمل على جهاز أو أكثر محليًا
- قاعدة البيانات المحلية تستضيف المعاملات اليومية
- يتم حفظ كل تغير في سجل حركة مع مرور الوقت
- إذا انقطع الإنترنت، يستمر العمل في الوضع المحلي

### التشغيل الموزع لاحقًا

- يمكن إضافة خادم مركزي أو قاعدة مركزية للنسخ الاحتياطي
- يتم ربط الفروع عبر مزامنة آمنة
- تُسمح المزامنة فقط بعد تأكيد النزاهة وسلامة البيانات

---

## 4) المكونات التقنية المقترحة

### مكونات القاعدة

- قاعدة بيانات محلية: SQLite أو PostgreSQL محلي في خادم الفرع
- واجهة مستخدم: Web app + PWA أو Desktop app مع دعم RTL
- نظام ملفات: الصور، PDFs، ملفات الموردين
- OCR محلي: لا يعتمد على اتصال الإنترنت

### التقنيات المحتملة

- Frontend: React + TypeScript + Tailwind
- Desktop/PWA: Electron أو PWA Hybrid
- Backend: Node.js أو .NET حسب القرار النهائي
- DB: PostgreSQL أو SQLite حسب البيئة
- OCR: Tesseract أو محرك محلي مشابه

> هذا ليس قرارًا فنيًا نهائيًا، بل إطار تقييم أولي يجب أن يمر عبر Decision Matrix لاحقًا.

---

## 5) مخطط تدفق البيانات

### أ) الاستيراد

1. ملف المورد يُرفع إلى النظام
2. يتم استخراج البيانات الأولية
3. يتم عرض البيانات في شاشة مراجعة بشرية
4. يوافق المسؤول على التعديل أو الإلغاء
5. يُحفظ المنتج أو دفعة جديدة في المخزون فقط بعد اعتماد

### ب) البيع

1. يختار المستخدم المنتج
2. يتحقق النظام من المخزون المتاح
3. يطبق FEFO
4. يُسجل البيع في الفاتورة
5. تُحدث حركة المخزون وتُكتب إلى السجل

### ج) المرتجعات

1. يتم تحديد الفاتورة الأصلية
2. يراجع النظام المنتج والدفعة
3. يتم إنشاء حركة مرتجع مستقلة
4. ينعكس التعديل في المخزون وسجل المحاسبة

---

## 6) حدود نظام MVP

يجب أن يتضمن MVP ما يلي:

- كتالوج منتج
- دفعات وصلاحية
- استيراد ملفات المورد
- مراجعة بشرية قبل الحفظ
- شراء ومورّدون
- نقطة بيع ووردية
- صفقات ومبيعات ومرتجعات
- تقارير أساسية
- مدقق/سجل تدقيق

لا يشمل MVP:

- العيادة كاملة
- جدول الأطباء المتقدم
- الوصفات الإلكترونية
- EMR كامل
- إدارة المرضى المتقدمة

---

## 7) المخاطر المعمارية الرئيسية

- ضعف الإنترنت
- انقطاع الكهرباء
- تراكم بيانات الطلبات والملفات
- فقدان الصور أو الدفعيات عند الاستيراد
- تعارض البيانات بين عرض المخزون والفواتير
- تغيّر سعر الصرف بين الشراء والبيع

الحلول المقترحة:

- حفظ محلي فوري
- نسخ احتياطي دوري
- ربط كل حركة بالمرجع الصحيح
- فصل كتالوج المنتج عن Batch Inventory
- الاحتفاظ بسجل صرف/بيع/إرجاع منفصل

---

## 8) القرار التالي

المرحلة القادمة تحتاج إلى:

- مقارنة حلول التقنية المتاحة
- تحديد نوع قاعدة البيانات المناسبة لكل فرع
- تقييم ما إذا كان الحل أفضل كـ WebRTC/PWA أم Desktop App
- اختيار نموذج مزامنة نهائي إن وُجد

هذا الملف يُعد أساسًا تحليليًا وليس قرارًا نهائيًا، وسيُعاد تعديله بعد اعتماد المالك والاختيار الفني.
